# Витрина продаж: сборка и сверка с 1С

Короткая инструкция для передачи. Всё, что нужно, чтобы собрать витрину с нуля
и проверять расхождение с 1С.

---

## 1. Одна команда — полная пересборка

```bash
cd /home/dev/airflow
PYTHONPATH=dags python3 -m core.tools.rebuild_sales --start 2026-06-15 --from-scratch
```

Что делает по шагам:

| # | Шаг | Комментарий |
|---|---|---|
| 1 | Миграции структуры `etl_meta` | 001/004/005/006 — идемпотентные DDL |
| 2 | Проверка конфига | регистр `sales` должен быть в `etl_meta.registers` |
| 3 | **Sync** | создаёт таблицы фактов `sales` / `sales_positions` из мэппингов — их DDL нет в миграциях, только в конфиге |
| 4 | Миграция `007_dim_layer.sql` | 8 справочников `dim_*` + 9 FK-колонок + индексы |
| 5 | TRUNCATE фактов | только при `--from-scratch`; **справочники не трогаются никогда** |
| 6 | `full_period` | загрузка из 1С за период; при гонке с живой 1С повторяется до 3 раз |
| 7 | `load_dim_names` | имена справочников из 1С — обязательный шаг |
| 8 | `sales_recon --strict` | **критерий успеха**: закрытые дни сходятся в ноль, иначе выход с кодом 1 |

Полезные флаги:

```bash
--dry-run          показать план и выйти
--start/--end      период (обычные даты; end исключительно, по умолчанию завтра)
--verbose          полный лог Airflow и тексты SQL (по умолчанию скрыты)
--from-scratch     очистить факты перед загрузкой
```

Ориентир по времени: ~6 минут на 50 дней (≈98 тыс. документов / 138 тыс. строк).

## 2. Сверка разницы с 1С — основной инструмент

```bash
python3 docs/audits/sql/sales_recon.py                       # последние 30 дней
python3 docs/audits/sql/sales_recon.py --start 2026-06-15 --full
python3 docs/audits/sql/sales_recon.py --strict              # код возврата 1 при расхождении
```

Как читать:
- **✅** — день сошёлся с 1С в ноль (такие скрыты, показывается счётчик)
- **⚠️ частичный день** — сегодня; небольшая дельта в минус — норма (инкремент отстаёт на 5–25 мин)
- **❌** — день разъехался:
  - дельта **в минус** (у нас меньше) → в 1С дописали задним числом. Лечится перезапуском сборки за этот период
  - дельта **в плюс** (у нас больше) → в 1С удалили строки или перепровели документ другой датой. Нужен разбор анти-джойном (примеры и журнал: `docs/audits/sales_aggregate_recon_2026-07-21.md`)

Расхождения появляются регулярно: бухгалтерия правит документы задним числом,
а retail сигналит об этом не всегда (см. раздел 5).

## 4. Что где лежит

**Код (в репозитории):**
- `dags/core/tools/rebuild_sales.py` — оркестратор сборки
- `dags/core/tools/load_dim_names.py` — загрузка имён справочников
- `dags/core/tools/run_full_period.py` — загрузка за период отдельно
- `docs/audits/sql/sales_recon.py` — сверка с 1С
- `dags/core/migrations/007_dim_layer.sql` — DDL справочников и FK
- `dags/core/migrations/008_register_dims_in_meta.sql` — регистрация справочников в конфигураторе (без неё их не видно в UI)
- `dags/core/migrations/etl_meta_dump.sql` — **снимок всего конфига** (регистры, источники, мэппинги, `post_load_sql`), без журнала загрузок

**Живёт в базе, а не в коде:**
- тексты `post_load_sql` (резолв guid→id и чистка устаревших строк) — в `etl_meta.register_targets`;
  восстанавливаются из дампа выше
- сами данные справочников — наполняются автоматически при сборке

**Восстановление конфига на чистой базе:**
```bash
psql -h 10.10.1.142 -U airflow_admin -d test -f dags/core/migrations/etl_meta_dump.sql
```
Миграция `002_sample_sales_register.sql` для этого **не годится** — там устаревший
конфиг без `pipeline_type` и без `post_load_sql`; оркестратор её намеренно не применяет.

## 5. Что важно знать про данные

**Инкремент (`sales_incremental_5min`, каждые 5 минут)** работает независимо от rebuild:
слушает retail, догружает свежие документы. Во время `--from-scratch` он блокируется
advisory-локом и один-два тика падают с понятной ошибкой — это норма, поток
восстанавливается сам.

**Границы retail** (подтверждено сверкой, есть доказательный пакет
`docs/audits/retail_signal_gaps_2026-07-27.md`):
- ЧекККМ — полное покрытие, сигнал на каждое изменение
- Реализация ТМЗ (B2B) — сигнал **только при создании**, правки не отражаются
- ОтчётКомитенту, возвраты без чека — в retail **отсутствуют**

Поэтому некассовые документы держит в актуальном состоянии не инкремент, а
периодическая сверка + пересборка. Инженер retail обещал часть этого починить.

**Справочники:** `id` раздаётся один раз и **никогда не меняется** — на них будет
ссылаться BI. Поэтому `--from-scratch` очищает только факты; в коде оркестратора
стоит явный запрет на очистку `dim_*`.

**`is_stub = true`** означает, что объект встретился в фактах, но его ещё нет
в справочнике 1С (или он удалён/архивный). На суммы не влияет — только на имя.
