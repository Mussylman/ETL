# Сессия 2026-06-10: дизайн редизайна конфигуратора на wizard'ы по типам 1С

Задача: спроектировать (без кода) набор wizard'ов под типы объектов 1С
поверх проверенного движка. Изучены: dags/core/* (контракт целиком),
etl_config_app/* (25 пишущих endpoint'ов), живая схема etl_meta.

Результаты:
- решение: [[Wizard'ы по типам 1С строятся над единым RegisterSpec и одним writer]]
- аудит: [[Латентные баги конфигуратора класса target_role]]

## Контракт движка (что реально читает ConfigLoader)

- registers: id, code, name, description, default_mode, retail_table, retail_uid_column
- register_sources: id, source_code, source_type(header|detail|standalone),
  mssql_schema, mssql_table, parent_source_id, join_type, join_key_source,
  join_key_parent, where_clause, priority
- column_mappings: source_column, target_column, is_expression, target_type,
  transform_type, transform_params, default_value, is_nullable
- source_unions + members, register_targets: target_schema/table, union_id|source_id,
  load_mode, upsert_keys, pre/post_load_sql, include_columns, priority, target_role

Механика per target: build SQL (source или union, JOIN parent при detail) →
extract MSSQL → transforms (binary auto + по конфигу + custom_python) →
include_columns split → dim dedup по upsert_keys → dim.updated_at из
retail-снимка/карты → pre_load_sql (duckdb) → load (insert/upsert/replace/
delete_insert_by_recorder) → post_load_sql.

key_column для инкремента выводится из source_type: standalone→_RecorderRRef,
header→_IDRRef, detail→через parent. Справочник как source_type='header'
получает корректный `_IDRRef IN (...)` бесплатно.

## План этапов

- **Этап 0 — фундамент**: RegisterSpec + spec_writer (транзакция) + валидатор +
  Sync-DDL (PK/UNIQUE/updated_at/FK) + минимальный патч движка (5 точечных
  правок + transform invert_bool) + golden-тест sales.
- **Этап A′**: текущий wizard переводится на spec_writer; фикс join_type;
  post_load_sql шаблонится (`{dim}_id` вместо sales_id); шаг «документы+VT»
  либо честно помечается как «только для recorder_type_map», либо переносится в C.
- **Этап B — Справочник → dim** (детально в плане ниже).
- **Этап C — Документ(+VT) → dim+fact**, UNION нескольких документов —
  чекбокс «добавить ещё документ» внутри C (и A), не отдельный wizard.
- **Этап D — InfoRg** (snapshot/history), позже. AccRg — пропуск.

## Wizard B (Справочник): вопросы → строки etl_meta

Вопросы аналитику (всё остальное вычисляется):
1. какой справочник (поиск по русскому имени через 1С API);
2. какие реквизиты грузить (чекбоксы, системные предотмечены);
3. имя целевой таблицы (default = code);
4. режим обновления (default: ночной full; incremental — только если есть
   retail-таблица с updated_at).

Порождает: 1 register (default_mode='full'), 1 source
(source_type='header', _ReferenceNNN, period_column=NULL), маппинги:
_IDRRef→id (uuid, binary_to_uuid, NOT NULL), _Code→code, _Description→name,
_Folder→is_folder (invert_bool, если иерархический), _ParentIDRRef→parent_id
(если есть в INFORMATION_SCHEMA), _OwnerIDRRef→owner_id (если подчинённый),
_Marked→is_deleted, реквизиты *RRef→`<имя>_id` uuid/binary_to_uuid,
остальные по типам MSSQL. 1 target: upsert по ['id'],
target_role='dimension', include_columns=все.

Иерархию НЕ спрашиваем — определяем по наличию _ParentIDRRef/_Folder.

## Wizard C (Документ+VT): вопросы → строки etl_meta

Вопросы: какой документ; какие VT (одна VT = один fact-target); реквизиты
шапки/VT; имена dim/fact; «только проведённые» (default да →
where_clause `{alias}._Posted = 0x01`).

Порождает: register (full_period), source header (_DocumentNNN,
period_column='_Date_Time'), source detail per VT (parent=header,
join_type='INNER', ключи _DocumentNNN_IDRRef ↔ _IDRRef), маппинги
(шапка: id/doc_date/doc_number/is_posted/is_deleted + реквизиты;
VT: doc_id (из _DocumentNNN_IDRRef), line_no + реквизиты), 2 targets:
dim←header (upsert ['id']), fact←detail (upsert ['doc_id','line_no'],
post_load_sql FK-резолв `{dim}_id`).

UNION-опция: union с output_columns = пересечение маппингов + members;
target переключается с source_id на union_id. Просто ветка генератора spec.

## Риски

- Sync-UNIQUE на грязных данных; составные типы 1С (_FldX_RRRef и пр.) —
  wizard обязан показывать компоненты; _Folder-семантика (0x00=группа);
  физические удаления из справочников при upsert не вычищаются (MVP:
  is_deleted-флаг, вычистка — фаза 2); построчный upsert медленный на
  больших справочниках (оптимизация execute_values — отдельно);
  транзакционность writer обязательна (сейчас autocommit per statement).
