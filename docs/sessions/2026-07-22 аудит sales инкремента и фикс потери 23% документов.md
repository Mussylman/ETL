# Сессия 2026-07-21/22: аудит sales инкремента и фикс потери 23% документов

## Контекст
DAG `sales_incremental_5min` работал 26 дней без контроля (2026-06-25 → 07-21). Задача: read-only аудит корректности данных.

## Ход
1. Начали глубокий аудит (workflow, 7 секций) — по ходу пользователь упростил задачу до **агрегатной сверки**: одинаковый период в MSSQL 1С и PG, только суммарные показатели.
2. Сверка `[2026-06-15, 2026-07-21)` нашла системную потерю: **дни full_period сходятся до копейки, дни инкремента −23% документов** (−11 457 док ≈ −2.63 млрд ₸), равномерно по всем recorder_type.
3. Причина: гонка сигнала retail и проведения 1С — watermark уезжал вперёд, overlap 5 мин меньше лага проведения (живой замер: 13% доков не проведены спустя 10–70 мин). 99.3% пропущенных на момент аудита уже были в 1С.
4. Фикс (идея пользователя «добирать по document_uid»): `DataChecker._get_tail_uids` + `TAIL_LOOKBACK=48h` — анти-джойн retail→DWH каждый тик. Первый тик: 2 227 строк за 6.7 сек.
5. Дыра закрыта двумя full_period (06-25..07-22: 122 395 строк; 06-15..06-26: 66 296 строк).
6. Остаток +20.1 млн = ровно 6 строк, удалённых в 1С после загрузки → удалены вручную по подтверждению (журнал в отчёте аудита).
7. По ходу поймали живые ретро-правки 1С (3 случая за час): перепроведение с другой датой ≠ удаление — **проверять движения регистра без фильтра по дате + шапку документа**. Один документ (58 млн) переехал с 07-16 на 07-22 — восстановлен перезагрузкой дня.
8. Итог: все закрытые дни сходятся с 1С в ноль.
