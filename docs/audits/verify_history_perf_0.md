## Перепроверка по пунктам (свои запросы, 10:58 UTC)

### 1. Количество и класс ошибок — ПОДТВЕРЖДЕНО (64 на момент аудита, сейчас 65)

- `load_history`: status='failed' → **65 строк**, все register_id=62, все run_mode='incremental'.
  Диапазон: 2026-06-27 09:45:02 … 2026-07-21 07:30:01 (UTC-naive). Всего в таблице: 7470 success + 65 failed.
- Логи Airflow (независимый grep):
  - файлов с «deadlock victim»: **65**, все — `attempt=1.log`; все 65 содержат «1205» и «UPP_JAN»;
  - `attempt=2.log`: **65** файлов; `attempt=3.log`: **0**;
  - обратная проверка: у **каждого** из 65 `attempt=2` соседний `attempt=1` содержит deadlock → других классов ошибок нет (65/65 один класс).
- Текст ошибки: `…deadlocked on lock | communication buffer resources … chosen as the deadlock victim. Rerun the transaction. DB-Lib error message 20018…` — классический MSSQL 1205 при чтении 1С (UPP_JAN).

### 2. Распределение по дням — ПОДТВЕРЖДЕНО

По `(started_at + 5h)::date` (Almaty): пик **2026-06-30 = 19**, **2026-07-01 = 13**; остальные дни 1–4;
2026-07-21 = 2 (05:20 и 07:30 UTC).

«Фон ~2.4/день»: средняя по всему периоду 64/27 ≈ 2.37 — включает пик; чистый фон после 01.07 ≈ 1.4/день.
Формулировка неточна терминологически, но порядок и вывод «продолжается ежедневно» верны.

### 3. Серии и восстановление — ПОДТВЕРЖДЕНО ТОЧНО

- Макс. серия failed подряд (window functions по всем runs register_id=62): **1**; макс. серия success: 842.
- У всех **65/65** failed следующий run — success.
- Гэп failed.started_at → next.started_at, без пост-аудитного id=7493 (снапшот аудитора):
  **min 2:04, max 3:05, avg 2:22.48** — совпадает с заявлением до секунды. С 65-м: max 3:22, avg 2:23.4.
- Гэп finished_at → ретрай: 2:01–2:03 = `retry_delay=timedelta(minutes=2)` из DAG (`retries=1`).
  Разброс от started_at объясняется длительностью падавшей попытки до deadlock.

### 4. Checkpoint и потери данных — ПОДТВЕРЖДЕНО

- `checkpoint_value IS NULL`: **65/65 failed**, **0/7470 success**.
- Механика (data_checker.py): watermark = `MAX(retail_updated_at)` из **загруженных строк** витрины
  (`checkpoint_value` — «аудит, не источник правды»), окно = [watermark − 5 мин overlap, now − 5 сек),
  upsert идемпотентен. Failed не грузит строк → watermark не двигается → ретрай перечитывает то же окно.
- Эмпирика: все 65 ретраев загрузили строки (rows_loaded 8–217) — окно действительно перечитано, потерь нет.
- Success/день: **288/288 во все 25 полных дней** 2026-06-26…2026-07-20 (ни одного дня ≠288);
  краевые частичные: 06-23 = 2 (тест), 06-25 = 76 (старт), 07-21 = 192 на 15:58 Almaty (~191 ожидаемо, */5).

### 5. error_message в load_history — ПОДТВЕРЖДЕНО

- `length(error_message)` = **ровно 2000 у всех 65** (обрезка).
- `ILIKE '%1205%'` → 0, `ILIKE '%deadlock%'` → 0; все 65 начинаются с `Execution failed on sql 'SELECT [sales].[_Fld17858]…`
  и обрываются внутри SQL — причина в load_history не видна, только в логах Airflow. Верно.

## Проверка типовых ловушек

| Ловушка | Результат |
|---|---|
| TZ +5ч (Almaty/UTC) | `started_at` — UTC-naive (сверено с now() БД). Дневные агрегаты пересчитаны с +5ч — пики те же. «Последний 21.07 05:20» у аудитора — сырое UTC (по Алматы 10:20); небрежность подачи, факт верен. |
| Год +2000 в MSSQL _Period | Не участвует: анализ по load_history/логам. |
| Знак возвратов (254) | Не участвует в проверке failed-запусков. |
| NaN в суммах | Не участвует (нет агрегатов по суммам). |
| Watermark по загруженным строкам | Подтверждено кодом data_checker.py и эмпирикой (ретраи грузят 8–217 строк). |
| Overlap 5 минут | WATERMARK_OVERLAP=5min подтверждён — усиливает вывод «потерь нет». |
| Частичный 2026-07-21 | Учтён: 192 success и 2 failed на 15:58 Almaty — не аномалия. |
| TZ-миграция ~2026-06-26 | Все failed с 06-27 — позже миграции, на анализ не влияет. |
