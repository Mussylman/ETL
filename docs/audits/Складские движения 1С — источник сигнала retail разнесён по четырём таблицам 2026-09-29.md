## Основной регистр
`РегистрНакопления.ПартииТоваровНаСкладахБухгалтерскийУчет` → `_AccumRg17576`.
Регистратор — `_RecorderTRef` (binary(4), номер типа документа) + `_RecorderRRef` (binary(16), guid).
Фильтр старой логики `Проведен ∧ ¬ПометкаУдаления` — без эффекта: у непроведённых/помеченных
регистраторов строк в регистре нет (2026: 0 строк), join к 15 таблицам документов не нужен.

## Сигнал retail
Retail — только сигнал (guid + `updated_at`); guid = `_RecorderRRef` (batch-lookup `WHERE _RecorderRRef IN (0x…)`,
как у продаж; тип не нужен — guid уникален). Последние 50 `stock_documents.document_uid` — 50/50 найдены.
Но `stock_documents` покрывает **34 из 1495** регистраторов за 28.09 — остальное в других таблицах:

| регистратор | сигнал retail |
|---|---|
| ПоступлениеТоваровУслуг, КомплектацияНоменклатуры, СписаниеТоваров, ОприходованиеТоваров, Пересортица ТМЗ, ПринятиеКУчетуОС, ПередачаМатериаловВЭксплуатацию, ВозвратТоваровПоставщику | `stock_documents.document_uid` (100%) |
| ПеремещениеТоваров (1161/сутки) | `transfers.guid` |
| КорректировкаКачестваТоваров | `adjustments.guid` |
| РеализацияТоваровУслуг, ВозвратТоваровОтПокупателя | `sales.document_uid` |
| ОтчетОРозничныхПродажах, ПоступлениеДопРасходов | **нет** — только hot/sweep |

У всех четырёх таблиц есть `updated_at`. Change-provider должен уметь объединять несколько таблиц сигнала.

Связано: [[Сигнал retail не значит, что документ готов в 1С — change-provider различает ready, pending и deleted]].

## Решения по заказу поставщику и цене (аудит 2026-09-30, проведённые поступления 2026)
4282 документа, 37 286 строк, 36 494 пары (поступление, номенклатура).

**Заказ поставщику** — источники не конфликтуют ни разу:
| источник | пар | = строке «Товары» |
|---|---|---|
| A `Товары.ЗаказПоставщику` (`_Fld9683RRef`) | 35 186 (96,4%) | — |
| D регистр `ЗаказыПоставщикам` (регистратор = поступление) | 35 186 | 35 186, конфликтов 0 |
| B основание шапки = ЗаказПоставщику | 16 633 | все совпадают |
| C основание → ПриходныйОрдер → Заказ (и строковый `ПриходныйОрдер`) | 18 549 | все совпадают |
B и C не пересекаются и вместе дают подмножество A. 1308 пар (3,6%) без заказа ни в одном источнике.
Рекомендация: A — построчно, без цепочки; D — сверка.

**Цена** — товар в нескольких строках одного поступления: 386 пар (1,1%, 131 документ), с разной ценой 87.
Различаются только количество и цена (единица, характеристика, серия, коэффициент, заказ, склад — одинаковы):
это одна позиция, разбитая на строки. Невзвешенный AVG ≠ взвешенной цене в 74 из 87. Стоимость партии
в регистре = цена / 1,16 (без НДС 16%). Соединение регистра со строками по (ДокументОприходования,
Номенклатура) без агрегации размножает 6025 строк регистра — AVG старой обработки выглядит способом
схлопнуть этот JOIN, а не бизнес-правилом. Рекомендация: Σ Сумма / Σ Количество по паре.

**Сигнал retail** — UNION четырёх таблиц без пересечений guid и без разных `updated_at` у одного guid
(сутки: 3054 guid, неделя: 21 077). Но `sales` — только `doc_type IN (6, 10)` (реализации, возвраты):
`doc_type = 8` (кассовые чеки, ~1478/сутки) в регистре партий не бывают никогда (0/1478) и навсегда
остались бы pending в хвосте.
