Замер A (12:10–12:15) для сравнения: источник 12:09:58→12:12:54; watermark 12:02:52; etl_updated 12:10:07; checkpoint id=7489 `to=12:09:58`, loaded=66.

**Находка про checkpoint:** поле `max_retail_updated_at` в checkpoint — это max по **отсканированным** retail-строкам (≈ `to`), а **не** watermark. Реальный watermark = MAX(`sales.retail_updated_at`) по витрине: даже после прогона 7496 (loaded=30) он остался 12:23:01 — все 30 загруженных строк были из overlap-зоны ≤ 12:23:01. Проверка согласованности: `watermark_from` следующего прогона = watermark витрины − 5 мин (12:18:01 = 12:23:01 − 5:00) — механика подтверждена по 3 подряд прогонам. Имя поля вводит в заблуждение при мониторинге.

## 2. Лаги (одна python-сессия, запросы встык)

| Лаг | Формула | Замер A (12:13) | Замер B (12:39) |
|---|---|---|---|
| **source lag** | now(Almaty) − MAX(ims_db→Almaty) | ~19 c | **33 c** |
| **data ETL lag** | MAX(ims_db→Almaty) − watermark | **10 мин 02 c** | **15 мин 53 c** |
| **pipeline lag** | now(Almaty) − MAX(etl_updated_at) | 3 мин 07 c | **4 мин 20 c** |

- Источник — real-time (лаг секунды).
- **Pipeline lag стабильно < 5 мин** — DAG честно отрабатывает каждые 5 минут и трогает витрину.
- **Data ETL lag «дышит» 10–16+ мин** и движется рывками: watermark стоит (12:23:01 держался с прогона 12:33 по 12:40+), затем скачком догоняет, когда изменения retail становятся видны в MSSQL-регистре. Т.е. лаг данных определяется не расписанием DAG, а **лагом видимости документов в MSSQL (1С)** — retail-строка появляется на 10–20 мин раньше, чем соответствующие строки регистра в UPP_JAN.

## 3. «Новее watermark» ≠ «недогружено» — split (замер B, watermark 12:23:01)

Строк retail с updated_at(Almaty) > watermark: **57** (все document_uid — валидные uuid, дублей нет).
Независимая перепроверка №2 счётом в UTC без Almaty-конверсии: **59** (спустя ~70 c; +2 — дрейф живой БД, методики согласованы). В замере A было 36 — число растёт, пока watermark стоит.

| Категория | Кол-во | Интерпретация |
|---|---|---|
| **(а) uid ЕСТЬ в public.sales** — настоящий backlog по продажам | **0** | нет ни одного загруженного документа с более свежим изменением в retail — витрина не «отстаёт» ни по одному своему документу |
| **(б) uid НЕТ в public.sales** | **57** | см. разбор ниже |
| Перепроверка (б) обратной логикой NOT EXISTS | 57 = 57 | сходится |

Разрез (б) по `to=12:39:58` последнего прогона: **57 уже сканировались и не загружены** (на момент extract в MSSQL-регистре не было строк по этим документам), **2 — ещё не сканировались** (изменены после `to`). Типы документов (б): (doc_type, sale_type, status) = **(8,1,1)×55 «Чек ККМ», (6,1,1)×3 «Продажа», (10,2,1)×1** — те же рабочие типы, что успешно грузятся, т.е. это не «мусорные не-sales документы», а продажи, которых **ещё нет в MSSQL-регистре** (лаг проведения/репликации 1С) либо которые в регистр не попадут (не проведён/удалён).

**Почему «новее watermark» ≠ «недогружено»:** watermark = MAX(retail_updated_at) только по **реально загруженным** строкам. Overlap 5 мин заставляет каждый прогон перечитывать [watermark−5мин, now−5с], поэтому документы категории (б) продолжают сканироваться, пока watermark не уйдёт от них дальше 5 минут. Санити-проверка ключа (иначе «(а)=0» был бы артефактом): из 143 retail-доков за час ДО watermark 92 находятся в sales по recorder — join-ключ работает; 51 отсутствующий — зона секции полноты (missing-обработка).

Примеры (б), uid | updated_at(Almaty):

- `0b4ab6b1-84d5-11f1-8104-bc97e145c062` | 12:24:53

## 4. Текущее необработанное окно [watermark−5мин, now−5с)

Замер B: окно **[12:18:01, 12:39:24)** = **81 строка / 81 документ** (min updated 12:18:20, max 12:38:54).
Три независимых замера согласованы: Almaty-счёт 81 (12:39:26) → UTC-счёт 84 (12:40:22) → `changes=83` в checkpoint прогона 7496 (`to=12:39:58`). Дрейф ±1–3 — новые продажи за секунды между замерами. Объём окна (десятки строк) прогон обрабатывает за ~6 c (7496: 12:40:03→12:40:09) — запас производительности большой.

Max changes за прогон 179, сумма за сутки 10 506.

### Вердикт по свежести

- **Механика инкремента — OK:** сетка 5 мин держится без пропусков, fail'ы самовосстанавливаются, watermark не теряется, окно обрабатывается за секунды. Pipeline lag стабильно в бюджете «5 мин + прогон».
- **Фактическая свежесть данных — WARNING (10–35 мин, не 5):** data ETL lag определяется лагом видимости документов в MSSQL-регистре 1С (retail опережает UPP_JAN на 10–20 мин), watermark движется рывками. Это свойство источника, а не дефект DAG, но потребителям витрины надо озвучивать SLA «до ~30 мин», а не «5 минут».
- **Настоящий backlog по продажам = 0:** ни один загруженный документ не имеет непринятых изменений. Все 57 «новее watermark» — документы, ещё не материализовавшиеся в MSSQL-регистре.
- **Риск (смежная секция полноты):** защита от отставшей видимости — только 5-мин overlap. Если строки регистра MSSQL появляются позже, чем watermark уходит на 5+ мин вперёд, документ выпадает навсегда (подтверждено секцией целостности: 7 доков без позиций, 21 без шапки, застыли с июня). Рекомендация: увеличить overlap до p99 лага видимости (~30–40 мин) или добавить пост-валидацию/повторный скан хвоста.
- **Гигиена мониторинга:** (1) checkpoint-поле `max_retail_updated_at` — это max отсканированного, не watermark: переименовать или добавить реальный watermark в checkpoint; (2) устаревшую копию `bd_retail` на 10.10.1.142 (стоит с 2025-11-11) убрать или явно пометить, чтобы свежесть не мерили по ней.
