| nds | 0 | |

| **summands** | **67 649** | 476 → 67 460 (81%), прочие типы → 100% |

Перепроверено вторым способом (`::text = 'NaN'`) — числа совпадают (дрейф −3 на живой БД).

Паттерн 216 строк: register-поля (stoimost, kolichestvo) заполнены, doc-поля (summa, tsena, nomerstroki) = NaN → join строки регистра к строке табличной части документа не нашёл соответствия (перманентный дефект матчинга по номеру строки, ~6 строк/день, продолжается по сегодняшний день). Пример: position id=135577 (415, line_no=2, stoimost=149990, summa=NaN, period 2026-07-21 11:27).

**Почему CRITICAL:** в Postgres `NaN` заражает агрегаты — `SUM(summa)` за любой день, где есть хоть одна NaN-строка (а это **все** дни), возвращает NaN. То же для evrika_* почти по любому срезу. BI-отчёты по этим полям либо ломаются, либо вынуждены фильтровать вручную.

**Рекомендация:** в loader конвертировать pandas NaN → NULL перед INSERT (NULL агрегаты игнорируют); существующие NaN — одноразовый UPDATE (вне рамок этого read-only аудита); разобрать матчинг строк табличной части для 216 строк.

### Побочная находка (WARNING): `etl_loaded_at` хранится в смешанных TZ

- 27 267 строк sales (initial full load 2026-06-25): `etl_loaded_at` ≈ `etl_updated_at` → **Almaty** (писалось кодом ETL).
- 37 168 строк (incremental): `etl_loaded_at` ровно на 5ч меньше `etl_updated_at` → **UTC** (DEFAULT `now()` при TimeZone=Etc/UTC на сервере).
- Подтверждение: max(etl_loaded_at)=2026-07-21 **07:15:04** UTC = 12:15:04 Almaty = max(etl_updated_at) с точностью до мс.

Следствия: (а) сравнение etl_loaded_at с «Almaty now» даёт ложный запас −5ч у incremental-строк; (б) группировки по `date(etl_loaded_at)` смещают вечерние загрузки (после 19:00 Almaty) на «предыдущий» день у UTC-строк.

Вторая побочная находка: `max(etl_updated_at − etl_loaded_at)` = ровно 5ч 00м 00.6с по всей таблице ⇒ ни одна строка не имеет `etl_loaded_at` старше своего последнего прогона. Значит при инкрементальной перегрузке документа строки фактически пересоздаются (DELETE+INSERT), и `etl_loaded_at` **не** является датой первого появления строки, вопреки документации (`sales_load_modes.md`: «не обновляется при upsert»).

## Итоговая оценка секции

Жёсткая реляционная целостность пары `sales`/`sales_positions` — **в отличном состоянии**: 0 NULL-ключей, 0 дублей, 0 orphan'ов, 0 инверсий watermark'ов, 0 будущих дат, объёмы стабильны. Найдены три реальные проблемы:

1. **CRITICAL — NaN в numeric**: 216 строк с NaN в summa/tsena/nomerstroki (все дни, все типы) и 67+ тыс. NaN в evrika_bonusy/evrika_spisannye/summands. NaN отравляет SUM/AVG в Postgres — агрегаты по этим полям возвращают NaN за любой день. Нужен фикс loader'а (NaN → NULL) и разбор матчинга строк документов.
2. **WARNING — застывшие дыры инкремента**: 7 документов без позиций (один прогон 2026-06-30) и 21 документ без атрибутов шапки (doc_number/is_posted NULL, ~1/день, продолжается). Оба паттерна — read-skew при чтении MSSQL сразу после события retail; из-за неизменности retail.updated_at самолечения нет. Нужна пост-валидация с retry в incremental и точечная перегрузка.
3. **WARNING — смешанные TZ в etl_loaded_at** (Almaty у full load, UTC у incremental через DEFAULT now()) + пересоздание строк при перегрузке делает колонку непригодной как «дата первого появления».
