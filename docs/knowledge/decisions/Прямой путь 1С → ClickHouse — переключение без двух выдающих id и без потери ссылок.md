# Прямой путь 1С → ClickHouse — переключение без двух выдающих id и без потери ссылок

План переключения регистров с `1С → PostgreSQL → ClickHouse` на `1С → ClickHouse`.
Каждый пункт — следствие того, что обнаружено при проверке shadow, а не предположение.

## 1. Реестр документов переходит к прямому пути отдельной таблицей

Факты ссылаются на другие факты по суррогатному id: возврат — на исходную реализацию
(`doc_sale_id`), продажа — на заказ (`zakaz_id`). В shadow прямой путь только **читает**
эти id из `public.sales` / `public.orders` — их выдаёт старый путь.

Взять `public.sales` реестром после остановки старого пути нельзя по двум причинам:
- `period NOT NULL` — не вставить ключевую заготовку для документа, на который
  сослались, но который ещё не извлекали;
- старый путь **удаляет** строки документов, исчезнувших из 1С. Вернись документ —
  получит новый id, и ссылки на старый повиснут. Для реестра это недопустимо:
  id выдаётся один раз и не меняется никогда.

Значит: реестр документов — отдельная таблица `(id, recorder, recorder_type)`, строки
которой **никогда не удаляются**. Засевается id из `public.sales` / `public.orders`
с сохранением значений, последовательность продолжается с `max(id)+1`.

**Двух выдающих id одновременно быть не должно.** Поэтому передача — одномоментная:
засев реестра → остановка записи старого пути для этого регистра → прямой путь начинает
выдавать id сам. До этого момента прямой путь id документов только читает.

## 2. Останавливать старый путь — не через `registers.is_active`

`ConfigLoader.load_register` фильтрует `is_active = TRUE`. Прямой путь грузит тот же
конфиг регистра, поэтому `is_active = false` уронит и его. Нужен отдельный признак
«первый hop пишет в PostgreSQL», который читает только `incremental_dag`.

## 3. Порядок: заказы раньше продаж

Продажа ссылается на заказ. Если заказ появился в том же цикле, что и продажа, при
обратном порядке `zakaz_id` останется 0 до следующей пересборки партиции. Старый путь
закрывает это «поздним резолвом» в `post_load_sql` заказов; прямой путь — порядком
(priority) и stub-строкой в реестре документов по первому появлению ссылки.

## 4. Расписание прямого пути

| что | как часто | зачем |
|---|---|---|
| патч по набору изменений retail + добор хвоста | каждые 5 мин | основной инкремент |
| пересборка горячего окна (текущий и прошлый месяц) из 1С | раз в час | слепая зона retail: некассовые документы, возвраты без чека, правки B2B — сейчас их ловит `sales_reconcile` |
| сверка отпечатков 1С ↔ ClickHouse по всей истории | ночью | удаления и дрейф в закрытых месяцах; расхождение → пересборка месяца |

Патч и пересборка пишут в одну партицию, поэтому под одной блокировкой источника
(`pg_advisory_lock(int,int)` — не пересекается с блокировкой первого hop'а).

## 5. Что уже доказано на shadow

- полная пересборка из 1С совпала со старым путём побитно по всем колонкам, кроме двух,
  изменённых решением (продавец, `doc_sale`) — 4 месяца разных лет;
- эти две колонки совпали с независимой реализацией правил на T-SQL прямо по 1С;
- независимая сверка 1С ↔ ClickHouse выводится из метаданных и сходится побитно.

## 6. Что реализовано к переключению (2026-09-24)

| что | где |
|---|---|
| реестр документов `etl_meta.doc_key` + `doc_key_scope` (issuer `pg_facts` → `registry`, последовательность та же, что у фактов) | миграция 013, `registry.doc_ids` / `seed_scope` |
| признак `registers.pg_fact_write` — при discovery и в момент выполнения задачи | `incremental_dag.py` |
| единый DAG `analytics_sync`, группы из `etl_meta.ch_sync_group`, режимы patch / hot / sweep | миграция 014, `runner.py` |
| триггер `incremental → clickhouse_sync` создаётся, только пока у него есть группы | `incremental_dag.py` |
| процедура переключения одной командой, план по умолчанию | `core.tools.ch_cutover` |

Публикация для читателей ClickHouse — `EXCHANGE TABLES fact_X ↔ fact_X_direct`: имя не
меняется, у шапок добавляется колонка `id`; старая таблица остаётся под именем `*_direct`
замороженной копией. Заказы и продажи переключаются одной процедурой: переключи только
заказы — и `public.sales.zakaz_id` у новых продаж перестал бы разрешаться (заказы в PostgreSQL
заморожены).
