# Бренд лежит в иерархии номенклатуры, но не на фиксированном уровне

## Реквизита «Бренд» в базе нет
В конфигурации 1С реквизит объявлен — meta API его отдаёт. Физической колонки
в `UPP_JAN.dbo._Reference123` под него **нет** (как и под
`ГруппаНоменклатураУпр`, `КодНацКаталога`, `НаименованиеНацКаталог`).
В retail тоже пусто: `products.brand_id` заполнен у 0 из 123 938 строк,
таблицы `brands` не существует.

## Где бренд реально
В иерархии справочника — группы `_Folder=0x00` носят имена брендов.
Достаётся через `parent_guid` (self-ссылка на `dim_nomenklatura`).

**Но глубина ветвей разная, и бренд не на фиксированном уровне:**

| Ветка | Путь | Где бренд |
|---|---|---|
| Электроника | `Товары ← Телевизоры ← **Samsung** ← товар` | прямой родитель |
| Fashion | `Fashion ← **UCB** ← KIDS ← Женское ← Пуловер ← SS23 ← товар` | 2-й уровень, родитель = сезон |
| Материалы | `Материалы ← Комплектующие для ОС ← товар` | бренда нет |

Поэтому «бренд = родитель» — правило только для электроники. Топ «брендов»
по числу товаров выдаёт сезоны (`SS23`, `FW23`, `SS24`, `CarryOver`), а не
производителей. Универсального SQL-правила нет; нужен либо признак уровня,
либо справочник соответствий, либо доработка на стороне 1С.

## `_Folder` инвертирован
`0x00` = **группа**, `0x01` = элемент — прямой `binary_to_bool` даёт значение,
обратное смыслу реквизита «ЭтоГруппа». В мэппинге стоит `invert_bool`.
Проверено: 4 862 группы / 123 922 товара.

## Загрузка иерархии
Группы не продаются, поэтому фактами в `dim_*` не заводятся — их подтягивает
режим `hierarchy`, догружая предков по `_ParentIDRRef` до корня:

```bash
PYTHONPATH=dags python3 -m core.tools.load_dim_from_config --dim dim_nomenklatura --mode hierarchy
```

Сошлось за 6 проходов: 4167 → 611 → 75 → 6 → 2 → 1. Корней 13.
Единственное место, где строки в `dim_*` создаются не фактами.
