# Retail BD используется для инкрементальной загрузки

## Назначение
1С разработчики создали API который записывает изменённые документы в базу retail.
ETL платформа обращается к retail напрямую для обнаружения изменений.

## Подключение
```
PROD: PostgreSQL 10.10.1.99:5432/ims_db (power_bi_user), Airflow conn: bd_retail
Тестовая копия (устаревшая): 10.10.1.142:5432/bd_retail — не использовать для замеров свежести
```

## Ключевые таблицы
- `sales` — 1.3М+ записей, ключ `document_uid` (UUID документа 1С = наш recorder), `updated_at` (UTC)
- поля классификации: `doc_type` (6=Реализация ТМЗ, 8=ЧекККМ, 10=возвраты), `sale_type`, `document_status`

## Режим инкрементальной загрузки
1. Окно по `updated_at` от watermark (−5 мин overlap)
2. + добор хвоста 48ч: uid, отсутствующие в DWH (фикс 2026-07-22, см. [[Инкремент терял документы из-за лага проведения 1С больше overlap]])
3. `document_uid` → binary(16) → запрос в 1С MSSQL → UPSERT

## В конфигураторе
- `retail_table` = "sales", `retail_uid_column` = "document_uid"

## ⚠️ Границы контракта retail (установлено сверкой 2026-07-27)
Retail — журнал **кассовых операций**, покрытие типов документов 1С неравномерное:
- **ЧекККМ (476)** — полное покрытие, сигнал на каждое изменение ✅
- **Реализация ТМЗ / услуги (415)** — запись создаётся ОДИН раз; правки/перепроведение в 1С `updated_at` НЕ обновляют ⚠️
- **ОтчётКомитенту (352), возвраты без чека (254)** — в retail отсутствуют полностью ⚠️

Доказательный пакет: `docs/audits/retail_signal_gaps_2026-07-27.md`.

**Договорённость с инженером retail (2026-07-27)**: подтвердили, что услуги/реализации у себя не обновляют; обещали починить **до конца недели (~01.08.2026)**.
После их деплоя проверить:
1. `python3 docs/audits/sql/sales_recon.py` — красные дни по 415 должны перестать появляться;
2. точечно: перепроведённый документ 415 должен получить свежий `updated_at` в retail;
3. уточнить, вошли ли в фикс 352 и возвраты без чека — если нет, их по-прежнему закрывает еженедельная сверка + перезагрузка дня.
