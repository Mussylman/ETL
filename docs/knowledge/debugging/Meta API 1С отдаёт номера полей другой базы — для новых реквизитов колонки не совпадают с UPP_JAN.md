# Meta API 1С отдаёт номера полей другой базы: для новых реквизитов колонки не совпадают с UPP_JAN

## Симптом
Мэппинги регистра `order` в TEST ссылались на колонки, которых в `UPP_JAN` физически нет:
`_Document271_VT4708._Fld24661` (Ответственный), `_Fld26935/_Fld26936` (Эврика_Бонусы/Списанные),
`_Document271_VT4746._Fld27835/_Fld27836`, `_Document415_VT11106._Fld27840/_Fld27841` и т.д. — 19 из 123 мэппингов.
Раньше та же история с `_Fld25945` у номенклатуры.

## Причина
`http://192.168.18.224:8090/NikitaBase/hs/meta` — это база **NikitaBase**, а грузим мы из **UPP_JAN**.
Конфигурация одна, но нумерация `_FldNNNN` присваивается каждой базе при реструктуризации, поэтому
для реквизитов, добавленных позже ~`Fld24500`, номера расходятся (старые совпадают). Замер 2026-09-03:

| таблица | полей в API | не существует физически |
|---|---|---|
| `_Document271` | 81 | 16 |
| `_Document271_VT4708` | 41 | 9 (Качество 24506→физ. 24518, Ответственный 24661→24668, СкладОтгрузки 24710→24721) |
| `_Document271_VT4746` | 19 | 7 (Ответственный 24662→24669) |
| `_Document476` | 71 | 26 |
| `_Document476_VT13626` | 41 | 20 |

`register_sources.fields_cache` в конфигураторе тоже наполняется из этого API, так что Column Builder
показывает поля, которых нет в базе (backend теперь отклоняет поле без `mssql_column`, но кэш имён всё равно от другой базы).

## Как определять принадлежность колонки
Не по API, а по данным: взять TOP 200 непустых значений `_FldNNNRRef` и проверить `EXISTS` в таблице-кандидате
`_ReferenceNNN`. Так подтверждены для заказа: `_Fld24518RRef`→Качество (`_Reference97`), `_Fld24668RRef`→Пользователи
(`_Reference145`), `_Fld24721RRef`→Склады (`_Reference169`). Для числовых мер (Эврика_Бонусы) — сверять суммы с 1С-отчётом.

## Что делать дальше
Либо перевести meta API на UPP_JAN (правильно), либо при добавлении новых полей всегда сверять `mssql_column`
с `INFORMATION_SCHEMA.COLUMNS` целевой базы (уже делает backend `mapping_batch`) и подтверждать смысл по данным.

Связано: [[Колонка, добавленная через UI, доезжает до таблицы]], [[Recorder type хранится как название документа]].

## Рядом: union-член наследует мэппинги родителя
`QueryBuilder._build_union_member_query` собирает `column_map` по таблицам `[parent, detail]`: если у detail нет
мэппинга на целевую колонку из `output_columns`, берётся мэппинг шапки с тем же `target_column`. Так у услуг заказа
`raw_refs.sklad` получил СкладГруппа шапки (контрольный день order, 2026-09-03). Лечится явным NULL-мэппингом у detail
(`CAST(NULL AS binary(16))`, is_expression). Проверять на контрольном периоде: у ТЧ без реквизита колонка должна быть NULL.
