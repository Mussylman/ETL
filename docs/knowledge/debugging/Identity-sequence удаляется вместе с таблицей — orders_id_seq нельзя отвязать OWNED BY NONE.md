# Identity-sequence удаляется вместе с таблицей — orders_id_seq нельзя отвязать OWNED BY NONE

**Контекст.** Удаление замороженных PG-фактов (`public.sales`, `sales_positions`, `orders`, `order_positions`).
Реестр документов `etl_meta.doc_key` выдаёт id из последовательностей `doc_key_scope`, а у `sales` и `orders`
это были последовательности старых таблиц фактов: `public.sales_id_seq`, `public.orders_id_seq`.

**Ловушка.** `sales.id` — serial (`deptype 'a'`): `ALTER SEQUENCE public.sales_id_seq OWNED BY NONE` отвязывает
её, после DROP таблицы она живёт. `orders.id` — `GENERATED BY DEFAULT AS IDENTITY` (`deptype 'i'`):
`OWNED BY NONE` даёт `cannot change ownership of identity sequence`, а `DROP TABLE public.orders` удаляет её вместе
с таблицей — выдача id новым заказам сломалась бы.

Проверить тип: `pg_depend.deptype` для последовательности (`a` — serial, `i` — identity) или
`information_schema.columns.is_identity`.

**Решение (2026-10-07).** Для `orders` — новая standalone-последовательность `etl_meta.doc_key_orders_seq`,
продолжающая нумерацию: `setval` = GREATEST(`orders_id_seq.last_value`, MAX(id) в `doc_key` для orders), и
переключение `doc_key_scope` — в одной транзакции под `LOCK TABLE etl_meta.doc_key IN SHARE ROW EXCLUSIVE MODE`
(параллельная выдача id ждёт коммита; если вставка уже прочитала старую последовательность — совпадение id
нарушит UNIQUE (doc_table, id) явной ошибкой, а не испортит данные; следующий прогон возьмёт новую). Для
`sales` — `OWNED BY NONE`, `sales_id_seq` остаётся действующей. Затем таблицы — в `*_drop_pending`, обычные
прогоны analytics_sync, и только после PASS — DROP.

**Ещё одна ловушка того же cleanup.** `register_targets` sales/sales_positions/orders/order_positions — не
«мёртвый PG-путь», а конфигурация извлечения прямого пути (`ch_sync.source_params.target`,
`onec._get_active_targets()`): `is_active=false` остановил бы загрузку в ClickHouse. Их оставили активными, а
конфигуратор теперь не делает Sync PostgreSQL-таблиц для регистров с `pg_fact_write = false`.
