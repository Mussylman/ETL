# Сигнал retail не значит, что документ готов в 1С — change-provider различает ready, pending и deleted

## Симптом
Shadow-серия патч-циклов прямого пути 1С → ClickHouse: 7 циклов подряд
«изменений 121…192, 1С вернула 0, **удалены 121…192**». В ClickHouse при этом ничего не
удалялось (затронутых партиций 0), но лог утверждал обратное.

## Причина
Отчёт считал `deleted = changed − returned`: всё, чего 1С не вернула, — «удалено».
Retail сигналит раньше, чем 1С получает документ (в тот день регистр 1С стоял на 14:55
почти час, пока retail продолжал сигналить). Отсутствие документа в 1С смешивалось в
одну категорию из двух разных:
- документа ещё нет в 1С (новый) — трогать нечего, надо ждать;
- документ был и исчез (удалён/распроведён) — патч должен его убрать.

## Решение
Классификация — отдельный generic-модуль `dags/core/clickhouse/changes.py`, без имён таблиц:

    signal (окно + 15-дневный хвост) → valid (uuid, не пустая ссылка)
      → точный lookup в источнике       → ready          → патч
      → нет в источнике, нет в витрине  → pending        → ничего, остаётся в хвосте
      → нет в источнике, есть в витрине → actually_deleted → патч удаляет

Lookup готовности — `ETLEngine.ready_keys(target, keys)`: корневая таблица и ключ
выводятся из `register_sources` тем же правилом, что фильтр извлечения
(`ETLEngine._key_source`), с `where_clause` источника (у заказов — `_Posted`/`_Marked`).
Извлекаются только ready; если lookup нашёл документ, а извлечение — нет, публикация
отменяется и окно не двигается.

Watermark — конец окна в `etl_meta.ch_source_state`, не `MAX(updated_at)` факта. Pending
не в витрине, поэтому хвост (retail за 15 суток минус витрина) подхватывает их сам.
Если всё pending — ни извлечения, ни публикации, ни записи в историю.

## Проверка
- Реальный цикл: 12 в окне + 186 из хвоста → 162 ready, 36 pending, 0 удалено; 202609 опубликован.
- Контролируемый тест «все pending» (отдельный ключ состояния, реальные lookup'ы):
  66 → 0 ready / 66 pending / 0 deleted; витрина, история и основной state не тронуты.

## Попутно найдено
- **Retail сигналит не обо всех ЧекККМ**: за сентябрь 12 из 39 092 чеков (и 15 из 622 документов
  типа 254) без единого сигнала — в `bd_retail.public.sales` их uid нет ни в одной колонке. Их
  не видит ни старый путь, ни патч; ловит только пересборка горячего окна (rebuild 202609 подобрал).
- Отпечаток сверки разрешает ссылки через реплики `dim_*` в ClickHouse: новая номенклатура,
  которой ещё нет в реплике, выглядит как расхождение факта. Справочники публиковать до фактов.
