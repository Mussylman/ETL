# Upsert не удаляет исчезнувшие строки документа при перепроведении

## Симптом
Еженедельная сверка показывала стабильную дельту +47 млн ₸ на 2026-07-29, которая не уходила после перезагрузки дня через full_period.

## Причина
Документ «Реализация ТМЗ» №87000001933 перепровели в 1С: **было 8 строк, стало 4**. Наш upsert идёт по ключу `(recorder, recorder_type, line_no)` — он обновил строки 1–4, а строки 5–8 остались висеть с устаревшими суммами. Ни один существующий механизм их не убирал:
- `missing-delete` в `_run_incremental` удаляет только документ целиком (по `recorder`), когда его вообще нет в 1С;
- full_period тоже работает upsert-ом — перезагрузка дня лишнее не чистит.

Масштаб: за месяц инкремента — 4 строки / 1 документ на 90 533 строки. Редко, но накапливается и искажает суммы.

## Решение: правило «строки старше последней загрузки документа»
Ключевое наблюдение: движок ставит `etl_updated_at = _now_local()` одним значением на весь DataFrame прогона. Значит **внутри одного документа все актуальные строки имеют одинаковый (максимальный) `etl_updated_at`**, а строки со старым временем — исчезнувшие из источника.

Стейтмент добавлен в `post_load_sql` target-а 81 (`sales_positions`), выполняется на обоих путях загрузки:

```sql
DELETE FROM public.sales_positions p
USING (
    SELECT recorder, recorder_type, MAX(etl_updated_at) AS last_load
    FROM public.sales_positions
    WHERE (recorder, recorder_type) IN (
        SELECT DISTINCT recorder, recorder_type FROM public.sales_positions
        WHERE etl_updated_at > timezone('Asia/Almaty', now()) - interval '60 minutes')
    GROUP BY recorder, recorder_type
) t
WHERE p.recorder = t.recorder AND p.recorder_type = t.recorder_type
  AND p.etl_updated_at < t.last_load - interval '30 minutes';
```

Две защиты:
- **окно 60 мин** — ограничивает работу документами текущего прогона; с индексом `idx_sales_positions_etl_updated_at` стоимость 48 мс вместо 566 мс полного скана и не растёт с размером таблицы;
- **зазор 30 мин** — защита от грязного чтения: после перехода на `WITH (NOLOCK)` (см. [[Падения DAG из-за deadlock в MSSQL 1С лечатся NOLOCK]]) можно поймать документ в момент перепроведения и увидеть частичный набор строк. Разрыв внутри одного прогона (секунды) под правило не подпадает; реальный ретро-случай (строки загружены дни назад) — подпадает. Цена: если документ укоротили и перегрузили в пределах получаса, чистка отложится до следующей его загрузки.

## Проверка
- Правило прогнано SELECT-ом по всей таблице ДО применения: попало ровно в те 4 строки и ни в одну лишнюю из 122 тысяч.
- Разовая чистка: `DELETE 4` → все 30 закрытых дней сошлись с 1С в ноль.
- Боевой тест: документу подсажена фиктивная строка `line_no=99` с ретро-датой → после full_period осталось ровно 4 строки, фиктивная снесена, дубли/orphans/unresolved = 0.

## Что осталось незакрытым
Если строка исчезла у документа, который больше никогда не грузится (415 без сигнала retail — см. [[Retail BD используется для инкрементальной загрузки]]), чистка произойдёт только при ручном full_period на этот день. Ловится еженедельной сверкой `sales_recon.py`.
