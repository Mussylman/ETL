# Инкремент терял документы из-за лага проведения 1С больше overlap

## Симптом
За 26 дней работы `sales_incremental_5min` витрина недосчиталась **11 457 документов ≈ 2.63 млрд ₸** (~23% оборота). Дни, загруженные full_period, сходились с 1С до копейки — терял только инкремент. Обнаружено агрегатной сверкой день-к-дню (см. [[sales_aggregate_recon_2026-07-21]], `docs/audits/`).

## Причина
Гонка между сигналом retail и проведением в 1С:
1. Касса пробивает чек → retail мгновенно ставит `updated_at`.
2. 1С проводит документ в регистр `_AccumRg17844` с задержкой — **13% документов не проведены спустя 10–70 минут** (живой замер).
3. Тик инкремента видит uid в окне, идёт в MSSQL — движений ещё нет, документ не грузится.
4. Watermark = `MAX(retail_updated_at)` по **загруженным** строкам — двигается вперёд другими документами.
5. Overlap 5 мин не спасает: окно уезжает, retail второй раз не сигналит → документ выпадает навсегда.

## Решение (добор хвоста по document_uid)
`dags/core/extract/data_checker.py`: константа `TAIL_LOOKBACK = 48h` + метод `_get_tail_uids()`. Каждый тик, помимо основного окна, берём uid из retail за последние 48ч, отсутствующие в DWH (анти-джойн по `recorder`), и добавляем в пачку. Документ перепроверяется каждые 5 минут, пока 1С его не проведёт; не-продажи сами выходят из 48ч-окна. Watermark-логика не менялась: хвостовые документы пишутся со своей старой retail-датой и watermark не двигают.

Проверка: 99.3% пропущенных (11 703 из 11 785) на момент аудита уже были в 1С — добрались по uid. Первый тик с фиксом: 2 227 строк за 6.7 сек. Стоимость: ~500–900 uid в IN-списке на тик.

## Восстановление дыры
Два full_period (upsert, без truncate): `4026-06-25..4026-07-22` (122 395 строк, 143с) и `4026-06-15..4026-06-26` (66 296 строк, 91с). Итог: 33 из 36 дней — дельта 0.00; остаток +20.1 млн (+0.13%) — ровно 6 строк, удалённых в 1С после загрузки (upsert не удаляет; чек 46BA0002849 целиком, строка 87202000253, строки 6–9 87000001298).

## Уроки
- Watermark по сигналам retail ≠ гарантия доставки: retail знает «что-то изменилось», но не знает, доехало ли до регистра 1С.
- Агрегатная сверка день-к-дню с источником — самый быстрый детектор таких потерь; построчный аудит не понадобился.
- Upsert не удаляет строки, удалённые в источнике задним числом — нужен периодический reprocess последних дней (план: weekly DAG).
